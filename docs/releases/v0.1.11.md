## Summary

`parakeet-cli` v0.1.11 starts faster, holds less memory while idle, and transcribes faster. It also reports how long each recognition stage took. Transcripts are unchanged, and protocol 2 is unchanged.

Against v0.1.10 on an M2 Pro, with the INT8 model and five interleaved runs each:

| | v0.1.10 | v0.1.11 |
| --- | ---: | ---: |
| `serve` launch to ready | 0.791 s | 0.602 s |
| Memory at ready | 1110 MiB | 913 MiB |
| Inference on a 48 s recording | 1.431 s | 1.188 s |

## What's Changed

- `complete` events gain a `stages` object with the seconds spent in VAD, the mel spectrogram, the encoder, and the decoder. Clients that ignore unknown fields need no change.
- `serve` and `transcribe --session` write `Model loaded in …` to stderr with the VAD check and recognizer load times.
- The per-segment VAD check stops at the first chunk of speech. A segment still counts as speech exactly when it did before. A VAD error after that first speech chunk no longer fails the segment.
- On Apple silicon, the encoder uses one thread per performance core.
- The encoder no longer prepacks its weights. It loads faster and holds less memory, for about 2% slower inference.
- CI pins its actions to commit SHAs. `actions/checkout` and `Swatinem/rust-cache` now run on Node 24.

## Integration Migration

No change is required. A client can read `stages` from `complete` to see where a slow transcription spent its time.

## Validation

- 61 Rust tests pass
- the 48 s demo recording produces the same transcript as v0.1.10 in every run
- the synthetic audio regression suite gives the same results as v0.1.10 in all 8 cases
- the thread-count change was measured only on an M2 Pro; chips with 4 performance cores use 4 threads, untested

## Build from Source

```bash
git clone --branch v0.1.11 https://github.com/lucataco/parakeet-cli.git
cd parakeet-cli
cargo build --release --locked --bin parakeet
```
